What version control is

  • A tool that records changes to files: what, who, when, and why
  • Built for plain text: code, config, docs, tests, LaTeX
  • Like Wikipedia page history, or Track Changes, for your whole project
  • Backup: every state recoverable, copy off-machine → fixes 1
  • Reproducibility: tag the version that made the paper → fixes 2, 3
  • Collaboration: independent edits combined, conflicts surfaced → fixes 4

Git was written by Linus Torvalds in ~2 weeks to manage the Linux kernel, after the previous tool revoked its free licence.

Why Git won

  • Distributed. No single point of failure. Works offline.
  • Snapshots, not deltas. Each commit stores the whole tree; unchanged files deduplicated by hash.
  • Branches are pointers, not copies. Creating one is instant.
  • Built for thousands of contributors. Your group of 3 is fine.
  • GitHub / GitLab turned it into a network.

Vocabulary

RepositoryYour project folder plus a hidden .git/ holding the full history. You rarely look inside.
CommitA labelled snapshot of the whole project, with author, date, message, and a pointer to its parent.
Working treeThe files you actually see and edit.
Staging areaThe set of changes you have picked for the next commit. Lets you commit part of your edits.
Local repoThe copy on your machine. Full history. Works with no network.
RemoteA copy hosted elsewhere (GitHub). Your off-site backup and the meeting point for collaborators.
BranchA movable pointer to a commit. An independent line of work.
HEADWhere you currently are in the history.

The four places your code lives

git status is your friend. Run it constantly. It tells you which box each change is in.

Emphasise: commit is local. Nothing leaves your machine until push. Staging lets you split edits into separate commits.

A commit


commit 5d3e831e867d5a4f1a83750ad82fd46041ac58e5
Author: Ada Lovelace <ada@example.org>
Date:   Tue Nov 4 10:12:33 2026 +0000

    Fix wrap-around when glider reaches grid edge

diff --git a/life.py b/life.py
@@ -14,7 +14,7 @@ def neighbours(cell, width, height):
-        yield (x + dx), (y + dy)
+        yield (x + dx) % width, (y + dy) % height
  • Hash: ID computed from content + parent. Tamper-evident chain.
  • Author, date
  • Message: why, not what. The diff already says what.
  • Snapshot of every file.
  • Parent: makes it a history.

git log walks the chain. git diff a1f3 5d3e compares any two.

Branching

A branch is a pointer. Commits on it don't disturb main.

  • One branch per task. Short-lived. Named for the change.
  • git switch main flips your working tree back instantly.

Merging

Usually automatic

Different files, or different lines of the same file: Git combines them. No human needed.

Sometimes a conflict


<<<<<<< HEAD
    if count == 3:
=======
    if count in (2, 3):
>>>>>>> fix-glider

Same lines edited both sides. Git stops, marks the file, you pick. Then add + commit.

Conflicts are not failures; they're Git refusing to guess. We'll probably see one live at the end when the second PR lands.

Working with others: fork, clone, pull request

You don't need write access to contribute. That's the point of forks.

The everyday loop


git pull                        # start from the latest
git switch -c fix-glider        # branch per task
# ... edit ...
git status                      # what changed?
git diff                        # exactly what changed?
git add life.py test_life.py    # pick what goes in
git commit -m "Fix glider dying at diagonal births"
git push -u origin fix-glider   # first push of a new branch
# then open a Pull Request on GitHub
  • Commit often. Small commits are easy to review, revert, and bisect.
  • One idea per commit. Fix and reformat? Two commits.
  • Message: imperative, under ~70 chars, says why. Body if needed.
  • Pull before you push.

Spot the smell

Fine or not? Answer in chat before each reveal.

git commit -m "fix"Smell. Fix what? Future you, bisecting at 11pm, will hate this.
git commit -m "Clamp timestep to avoid NaN in leapfrog"Good. Imperative, specific, says why.
git add .venv/ data/*.hdf5Smell. Environments and big data don't belong in history. .gitignore them.
git add config.py  # contains API_KEY = "sk-..."Very bad. History is forever and clones are public. Rotate the key.
One commit, 47 files, "Refactor + fix bug + new plots"Smell. Unreviewable, unrevertable, unbisectable.
git push --force origin mainSmell. Rewrites shared history. Collaborators' clones now disagree with the remote.
git commit -m "WIP" on your own branch, tidied before PRFine. Your branch, your mess. Clean it up before anyone else reads it.
Committing final_v7.py next to final_v6.pySmell. That's what the history is for. One file, many commits.

What belongs in a repo

Yes
  • Source code, scripts, notebooks (outputs stripped)
  • Config, environment specs (requirements.txt)
  • Docs, tests, small test fixtures
  • Anything plain-text whose line diffs mean something
No
  • Simulation outputs, large data, figures you can regenerate
  • Binaries, __pycache__/, .venv/, build/
  • Editor and OS junk (.DS_Store, .idea/)
  • Secrets. Keys, passwords, tokens, personal data

Finding the commit that broke things: git bisect

Binary search over history. You say "good" or "bad", Git picks the next commit to test.


git bisect start
git bisect bad            # HEAD is broken
git bisect good v0.1      # this tag worked
# Git checks out the middle commit. Test it.
git bisect good   # or: git bisect bad
# ... repeat ~log2(N) times ...
# "abc123 is the first bad commit"
git bisect reset          # back to where you were
  • 40 commits → ~6 tests. 1000 commits → ~10.
  • Works even if you don't understand the code. You only need a test.
  • Automate: git bisect run python check.py (exit 0 = good).
  • Needs small commits with honest messages. This is why we nag.
Walk the animation: each step halves the range. Note detached HEAD state during bisect; always `git bisect reset` afterwards before branching.

Your turn: the glider died

Repo: github.com/WillJRoper/git-bisect-workshop

  1. Fork the repo on GitHub, then git clone your fork.
  2. Run python life.py glider. It should fly forever. It dies. Tag v0.1 worked.
  3. git bisect to find the commit that killed it. Read its diff.
  4. git bisect reset, then git switch -c fix-glider.
  5. Fix it. Add a test so it can't happen again. git add, git commit.
  6. git push -u origin fix-glider and open a Pull Request against the original repo.
